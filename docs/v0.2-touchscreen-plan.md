# v0.2 — Touchscreen mode plan

> **Status: all eight steps complete, verified on the panel.** Tap, one-finger
> scroll and long-press drag all work; 134 tests pass. See "Results" at the end.

Per spec §28 (v0.2). Required reading: `M14t_Touch_Manager_TZ.md` §7–8, §10, §22–23, §27.
v0.1 built the seam this plugs into — see `docs/v0.1-refactor-plan.md`.

## Goal

A second `GestureRecognizer`, registered in `TouchMode.makeRecognizer`, that
treats the panel as a touchscreen rather than a large absolute touchpad. Mouse
mode stays exactly as it is, as the fallback.

**Definition of Done** (spec §28) — in Safari or Chrome:

- a short tap presses the link or button under the finger;
- a vertical swipe scrolls the page;
- text is not selected while scrolling;
- the cursor is not dragged along during a scroll;
- long press then move drags an element.

## What the hardware dictates

Three findings from probing the panel change the design, and none of them are
guesses — see the Hardware facts section of `CLAUDE.md`.

**1. A stationary finger sends no coordinates.** While a contact is held still
the device reports only `ScanTime` (usage `0x0D:0x56`); X, Y and `TipSwitch`
stay silent. A recognizer driven purely by coordinate frames would therefore
*never* see a long-press deadline pass, because no frame arrives to check it
against. Long press cannot be implemented as "compare timestamps on the next
frame".

**2. `ScanTime` is a usable clock.** It advances by 100 units roughly every
10 ms — a ~100 Hz tick — and only while a contact exists. That is precisely the
heartbeat long press needs, and it comes from the device rather than a timer
racing the run loop.

**3. `ScanTime` marks report boundaries.** Values arrive per report in the order
`ScanTime, Y, X, TipSwitch`. A new `ScanTime` therefore means the previous
report is complete.

## Design consequences

**Feed `ScanTime` into the pipeline.** The driver currently ignores it. It
should produce a frame on `ScanTime` too, which solves the long press *and*
fixes the zigzag v0.1 deliberately preserved: with a report boundary to batch
on, a frame can carry a matched X/Y pair instead of a new X against a stale Y.

This is the report-level batching deferred from v0.1 (§Behaviour contract,
property 1). It is a behaviour change and belongs to exactly one commit, with
mouse mode's existing tests updated to describe the new cadence rather than
quietly re-recorded.

**Long press is checked on every frame**, including `ScanTime`-only ones, by
comparing against the contact's start timestamp. No timers, no threading.

## New pieces

| Type | Responsibility |
|---|---|
| `GestureConfiguration` | Thresholds, delays, sensitivity — one value type, spec §4 |
| `TouchscreenRecognizer` | The state machine below |
| `ScrollEventEmitter` | Pixel-unit scroll `CGEvent`s, spec §23 |
| `RoutingEventEmitter` | Sends scroll actions to one emitter, mouse actions to the other |

`InputAction` already has every case needed — `tap`, `scroll`, `dragBegin/Move/End`.
`MouseEventEmitter` currently maps `tap` and `pointerMove` to nil; that changes here.

## State machine (spec §22)

```
idle
 └─ contact ──▶ possibleTap
                 ├─ release, little movement, under tapMaxDuration ──▶ tap ──▶ idle
                 ├─ movement > scrollThreshold ─────────────────────▶ scrolling
                 └─ held > longPressDelay ─────────────────────────▶ dragging

scrolling  ── movement ──▶ scroll(delta)          ── release ──▶ idle
dragging   ── movement ──▶ dragMove               ── release ──▶ dragEnd, idle
```

**The lock is the point.** Once `scrolling`, the gesture stays `scrolling` until
release — the long-press deadline is not consulted any more. Without that, a slow
scroll turns into a drag halfway through and selects text, which is the failure
the DoD calls out.

Starting defaults, all configurable: `tapMovementThreshold` 8 px,
`tapMaxDuration` 300 ms, `scrollThreshold` 10 px, `longPressDelay` 400 ms
(spec §8). These are guesses to be tuned on the panel, not measurements.

## Cursor policy (spec §10, §35)

The goal is that the arrow does not chase the finger. Three approaches were
measured on the panel, with a scrollable page on the M14t and the cursor parked
on the MacBook:

| Approach | Cursor | Scroll arrives |
|---|---|---|
| `location` set, HID or session tap | warps to the point | yes |
| `CGEventPostToPid` to the owning app | **stays put** | **no** |
| One warp at gesture start, then no `location` | moves **once** | yes |

A scroll event has no location parameter in its constructor, and setting
`CGEvent.location` on one does not act as a delivery address — it warps the
pointer, at both tap levels. Posting straight to the owning process (Brave,
resolved from `CGWindowListCopyWindowInfo`) left the cursor alone but scrolled
nothing: without the window server's hit testing the app matched the event to no
view.

So the cursor **must** be where the scroll should land, and "never move the
cursor" is not achievable with public APIs. The third row is the design:

| Gesture | Cursor |
|---|---|
| Tap | placed at the touch point for the click; possibly restored afterwards |
| Scroll | placed at the touch point **once**, at gesture start, then left alone |
| Long press + drag | placed at the grab point and carried with the drag |
| Mouse mode | unchanged — the finger drags the arrow |

Measured: after a single warp and **25** scroll events the cursor had not moved
a pixel from the landing point. The arrow demonstrably does not follow the
finger, which is what §35 asks for; it lands once where the gesture began.

For tap, `CGWarpMouseCursorPosition` can put the cursor back after the click —
the same call used above, and instantaneous. Whether the round trip is visible
is judged on the panel in step 3; if it flickers, drop the option from §10
rather than ship a setting that flickers.

## Scroll generation (spec §23)

`CGEvent(scrollWheelEvent2Source:units:.pixel:wheelCount:…)`. The sign is
**not** to be hardcoded — determine it on the device and drive it from a
`naturalScroll` setting, defaulting to touchscreen-like (content follows the
finger).

Pipeline per spec §23: raw delta → dead zone → sensitivity → optional low-pass
smoothing → event. No momentum physics in v0.2.

## Steps

Each is one commit, `swift build && swift test` after each (spec §33.4–5).

1. **`GestureConfiguration`** + CLI flags, unused. Pure addition.
2. **Report batching.** Driver emits a frame per report, keyed on `ScanTime`.
   Mouse-mode tests updated to the new cadence — the one commit in this plan
   that deliberately changes existing behaviour.
3. **`TouchscreenRecognizer`**, tap only: tap, and the movement/duration limits
   that stop it being a tap. Fully tested, not yet reachable from the CLI.
4. **Long press to drag** — the branch that needs `ScanTime` frames.
5. **Scroll**, recognizer side: `scroll` deltas and the gesture lock.
6. **`ScrollEventEmitter` + routing**, and `MouseEventEmitter` learns `tap`.
7. **Register the mode** in `TouchMode.makeRecognizer`; `--mode touchscreen`
   starts working, and its "not implemented" guard and test are replaced.
8. **Tune on hardware** against the §30 acceptance list.

## Tests (spec §27)

Tap: down→up; down→tiny move→up. Scroll: down→move past threshold. Gesture lock:
scroll started, long-press deadline passes, still scroll. Drag: down→wait→move
gives `dragBegin` then `dragMove`; release gives `dragEnd`. Plus the boundaries —
movement exactly at each threshold, duration exactly at each deadline — since
v0.1 showed a strict-versus-inclusive comparison is easy to get wrong.

## Risks

**Thresholds are guesses.** Every default above needs tuning against the panel;
step 8 exists for that and is not optional.

**Batching changes mouse mode.** Step 2 alters behaviour that v0.1 froze
deliberately. It should be verified on hardware before the touchscreen work
stacks on top of it, so a regression is attributable.

**Scroll feel cannot be unit tested.** Sign, sensitivity and smoothing are
judged by hand on the device. Tests can only pin the arithmetic.

## Results

Verified on the M14t across several 90-second sessions, in a browser and in
Finder.

| | Outcome |
|---|---|
| Tap | A short touch clicks the link or file under the finger. |
| Scroll | A swipe scrolls; the cursor lands once and does not follow the finger. |
| Drag | Press, hold, move drags real files in Finder — three clean drags in one session, `DOWN → 587 × DRAG → UP`. |
| Gesture leakage | None observed: `P sss… R [ mmm… ] R T R`, one restore per completed gesture, never two. |

**The starting thresholds were kept.** `scrollThreshold` 10 px,
`longPressDelay` 400 ms and `scrollSensitivity` 1.0 were guesses, and nothing on
the panel argued against them — a tap does not slip into a scroll, and a hold
reaches the drag deadline without drifting out of the threshold first. They stay
adjustable from the command line, and step 8 can be revisited if daily use
disagrees.

**Scroll direction was measured, not chosen.** A positive `wheel1` moves the
content toward the beginning of the document, which is where a finger travelling
down should take it, so the finger delta maps through unflipped. Horizontal
scrolling was never exercised and assumes the same convention.

**Cursor restore is on by default.** The arrow is visible arriving and leaving —
unavoidable, since the window server draws it wherever the click put it — but
the round trip was judged acceptable, and an arrow parked in the middle of a
touchscreen is not.

### What was not covered

- Horizontal scrolling was never tested on the device.
- Multi-touch remains out of scope (spec §11); everything above is one contact.
- The panel reports pen usages inside the same descriptor, all still ignored
  (spec §12).
