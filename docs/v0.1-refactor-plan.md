# v0.1 — Architectural refactor plan

Per spec §28 (v0.1) and §34. Required reading before starting: `M14t_Touch_Manager_TZ.md` §4–6, §32–34.

## Goal

Split HID acquisition from gesture interpretation from event emission — **without
changing observable behaviour**. No new gestures, no GUI, no scrolling. The only
deliverable is a seam that v0.2 can plug a touchscreen recognizer into.

**Definition of Done** (spec §28):

- current driver behaviour unbroken;
- architecture allows adding a touchscreen mode;
- `swift test` passes.

## Target data flow

```
IOHIDManager ─▶ HIDTouchDriver ─▶ TouchFrame ─▶ GestureRecognizer ─▶ InputAction ─▶ EventEmitter ─▶ CGEvent
               (IOKit only)      (raw+mapped)  (MouseModeRecognizer)              (MouseEventEmitter)
                                                └── pure, fully unit tested ──┘
```

`HIDTouchDriver` currently spans this entire chain: it opens the device, decides
that movement means drag, and posts `CGEvent`s itself. After v0.1 it only does
IOKit and frame construction.

## Behaviour contract to preserve

These four properties are what "behaviour unbroken" actually means. They are easy
to break silently, so each gets a test.

**1. One frame per HID value, not per report.** `handle()` reacts to each
`IOHIDValue` individually: X updates `currentRawX` then evaluates movement,
Y does the same, `tipSwitch` toggles contact
(`HIDTouchDriver.swift:197-206`). So a drag can be emitted from a new X against a
stale Y. The refactor emits one `TouchFrame` per HID value to reproduce this
exactly. Report-level batching is a **v0.2** decision — do not "fix" it here.

**2. Mouse-up fires at the last emitted point.** On release the driver posts at
`lastScreenPoint`, not at a freshly mapped position (`:222`). Same for the
release synthesised on device removal (`:123`).

**3. Auto-calibration applies to the event that produced it.**
`recordForAutoCalibration` runs *before* movement evaluation (`:197-198`), so a
sample that widens the range is mapped with the widened range. Frame construction
must keep that order.

**4. Movement threshold is per-axis, `>` not `>=`, in screen pixels** (`:231-232`,
default `1.5`).

## New types

```swift
struct TouchPoint {                    struct TouchFrame {
    let id: Int                            let contacts: [TouchPoint]
    let position: CGPoint      // screen   let timestamp: TimeInterval
    let rawPosition: CGPoint   // raw HID  var primaryContact: TouchPoint? { contacts.first }
    let isTouching: Bool               }
    let pressure: Double?
    let timestamp: TimeInterval
}
```

Mapping happens when the frame is built, so the recognizer never sees raw
coordinates and never touches `CoordinateMapper`. `rawPosition` is carried only
for diagnostics (spec §14). v0.1 always produces exactly one contact; the array
exists so multi-touch (§11) does not require changing the type later.

```swift
enum InputAction {                     protocol GestureRecognizer {
    case tap(position: CGPoint)            mutating func process(_ frame: TouchFrame) -> [InputAction]
    case pointerMove(position: CGPoint)    mutating func reset() -> [InputAction]
    case dragBegin(position: CGPoint)  }
    case dragMove(position: CGPoint)
    case dragEnd(position: CGPoint)    protocol EventEmitter {
    case scroll(deltaX: CGFloat,           func emit(_ action: InputAction)
                deltaY: CGFloat)       }
    case rightClick(position: CGPoint)
}
```

`process` returns an array because v0.2 gestures emit several actions per frame
(`dragBegin` + `dragMove`). v0.1 returns 0 or 1. `reset()` covers device removal:
it flushes a held contact instead of leaving the button stuck down.

Current mouse behaviour maps onto existing cases with no new ones needed:

| Today | InputAction | CGEvent |
|---|---|---|
| finger down | `.dragBegin` | `leftMouseDown` |
| finger moves past threshold | `.dragMove` | `leftMouseDragged` |
| finger up | `.dragEnd` | `leftMouseUp` |

## Steps

Each step is one commit, builds green, and runs `swift build && swift test`
(spec §33.4–5). Steps 1–3 are pure additions — nothing is wired up until step 4,
so the driver keeps working throughout.

**Step 1 — models.** Add `TouchPoint`, `TouchFrame`, `InputAction`. No behaviour.

**Step 2 — event emission.** Add `EventEmitter` protocol and `MouseEventEmitter`,
which absorbs today's `MouseEmitter` and maps `InputAction` → `CGEventType`. Add a
`RecordingEventEmitter` test double. Driver untouched.

**Step 3 — gesture recognition.** Add `GestureRecognizer` and
`MouseModeRecognizer`, holding the state machine lifted from the driver
(`isTouching`, `lastPosition`, `dragThreshold`). Tests are written here, derived
from the four contract properties above:

- down → `.dragBegin` at the mapped point;
- movement below threshold → nothing;
- movement above threshold → `.dragMove`, and `lastPosition` advances;
- movement while not touching → nothing;
- up → `.dragEnd` **at `lastPosition`**, not at the released point;
- `reset()` while touching → `.dragEnd`; while idle → nothing;
- down → up with no movement → exactly `[.dragBegin, .dragEnd]`, no stray move.

**Step 4 — wire it up (the risky one).** `HIDTouchDriver` builds a `TouchFrame`
per HID value and feeds a `TouchEngine` (recognizer + emitter); its own state
machine and direct `emitter.post` calls are deleted, and `deviceRemoved()` calls
`reset()`. Nothing else changes in this commit — review it against the four
contract properties before moving on.

**Step 5 — calibration.** Move calibration resolution and `ObservedRange` out of
the driver into a `CalibrationController`, leaving the driver purely IOKit. Adds
the `CalibrationStore` save/load/reset tests the spec requires (§27) and which do
not exist today.

**Step 6 — layout.** Move files into `Core/{HID,Display,Calibration,Gestures,Events}`
per spec §4. Pure moves, no edits, so the diff stays reviewable.

**Step 7 — the mode seam.** Add `TouchMode { touchscreen, mouse }`, a recognizer
factory, and a `--mode` flag defaulting to `mouse`. `--mode touchscreen` returns a
"not implemented until v0.2" error. This is what proves the DoD: v0.2 adds a
recognizer and registers it in the factory, touching nothing else.

## Explicitly out of scope

Threading changes (§25 — HID callbacks stay on the main run loop as today), the
hardcoded `displayIndex = 1` default (§32 violation, but changing it is a
behaviour change — v0.3 with display selection), scroll/tap/long-press (v0.2),
GUI (v0.3), report-level frame batching, and the `com.talesfonseca.*` identifiers.

## Risks

**No hardware.** The M14t is not attached, so behaviour preservation is verified
against the *semantics of the current code*, not against the panel. Every step
should say so rather than claiming the driver was tested. First run on real
hardware is the actual acceptance gate for v0.1.

**Latent quirks are being preserved on purpose.** Per-axis emission against a
stale opposite axis (property 1) and release-at-stale-point (property 2) are
arguably bugs. v0.1 keeps them so any regression is unambiguously the refactor's
fault; revisit in v0.2 with the device connected.

**Multiple matching HID devices.** The M14t exposes a "Pen and multitouch sensor"
interface; `deviceConnected` runs `resolveCalibration` per device, so a second
match silently overwrites calibration. Out of scope for v0.1, but do not make it
worse — device identification by VID/PID is spec §18, scheduled for v0.6
diagnostics.
