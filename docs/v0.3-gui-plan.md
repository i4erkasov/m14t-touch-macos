# v0.3 — macOS GUI

Per spec §28 (v0.3), §13–14, §19, §21. v0.1 built the layer separation and v0.2
the touchscreen mode; this puts a face on them.

## Goal

A menu-bar application: enable/disable, mode, gesture settings, display
selection, permission status. The CLI stays, as the development and debugging
entry point (spec §20 keeps the old installer for that).

**Definition of Done** (spec §28): SwiftUI app, menu bar, settings window,
enable/disable, mode, scrolling settings, display selection, permission status.

## Three decisions to take first

These shape everything else and are cheaper to settle now.

### 1. How the `.app` gets built

SwiftPM produces a bare executable; a menu-bar app needs a bundle with an
`Info.plist` carrying `LSUIElement` so it has no Dock icon. Three ways:

| | Cost |
|---|---|
| **Packaging script over SwiftPM** | Keeps `swift build` and `swift test` working, keeps the CLI, no new project file. Bundle assembled by a script. |
| Xcode project | Native bundling and signing, but `.gitignore` currently excludes `*.xcodeproj`, the workflow in `CLAUDE.md` is built on `swift test`, and the package would need restructuring. |
| Both | Two sources of truth that drift. |

**Proposed: the packaging script.** The whole test suite and every workflow
instruction in `CLAUDE.md` rests on SwiftPM, and none of it should be traded for
bundling that a fifteen-line script can do.

### 2. Permissions move to a new identity

Input Monitoring and Accessibility are granted per binary, keyed on its code
signature and path. A new `.app` is a new identity: **every permission has to be
granted again**, and the terminal's existing grants do not carry over.

Worse for development: an ad-hoc signature changes on every build, so each
rebuild can look like a fresh, unpermitted application. Mitigations, in order of
preference:

- develop against the CLI, which keeps its grants, and treat the `.app` as a
  release artefact;
- install to a stable path (`~/Applications/M14t Touch.app`) so the user grants
  once;
- sign with a stable ad-hoc identity rather than a fresh one per build.

This deserves a section in the README, since "I granted permission and it still
does not work" is otherwise the obvious support question.

### 3. Threading (spec §25)

Everything currently runs on the main run loop, which was right for a CLI and is
wrong once SwiftUI shares it: HID callbacks at ~100 Hz would compete with UI
rendering, and spec §24 asks for low latency and no blocked UI.

Target, as spec §25 sketches:

```
HID callback  →  touch queue (serial)  →  recognizer  →  emitter
                        ↓
                  @MainActor state  →  SwiftUI
```

This is the largest risk in v0.3 and the one place where a mistake is not
visible in tests: the pipeline is currently single-threaded by accident rather
than by design, and moving it needs the recognizer's state confined to the
queue. Diagnostics UI must be throttled (spec §24) — 100 frames a second into
SwiftUI would melt it.

## Steps

1. **Settings persistence** (spec §21). `AppSettings` in `UserDefaults`, separate
   from calibration, with the CLI still able to override. Pure, testable.
2. **Display selection** (spec §17). Replace the hardcoded `displayIndex = 1`,
   which §32 forbids, with a stored choice matched back to the same display on
   reconnect.
3. **Threading.** Move the pipeline onto a serial queue, publish state on
   `@MainActor`. Behaviour-preserving, verified on the panel before any UI
   arrives — a regression here must not be attributable to the GUI.
4. **App skeleton.** SwiftUI `App`, `LSUIElement`, menu-bar item, packaging
   script. No settings yet: just runs the driver and can quit.
5. **Menu** (spec §13): status, enable, mode, calibrate, settings, quit.
6. **Settings window** (spec §14): General, Touch, Calibration tabs.
7. **Permission status** (spec §19): show granted/required and a button to open
   the right System Settings pane; re-check when the app regains focus.
8. **Verify on the panel**, including the permission flow from a fresh grant.

## Out of scope

GUI calibration is v0.4 — the settings window shows the current calibration and
a button that runs the existing CLI flow until then. Start at Login is v0.5.
Diagnostics (spec §14's raw HID viewer) is v0.6.

## Risks

**The threading change is invisible to tests.** Steps 1–2 are pure and covered;
step 3 is neither, and its failure mode is a rare dropped or reordered event.
It gets its own hardware verification before any UI is stacked on it.

**Permissions will confuse.** The first `.app` run will look broken until both
permissions are granted to the new identity. Expect to spend time here that
looks like debugging and is not.

**SwiftUI on macOS 13.** The deployment target is macOS 13 (spec §32) while this
machine runs 26. Anything newer than 13 that creeps in will not fail here — it
will fail for someone else.
